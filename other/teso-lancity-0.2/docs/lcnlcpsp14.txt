BOOTP Fields Used by LCp

The following fields are required in the Bootp response returned to an LCp and thus must be present in the bootp table used by the server.

The hardware address of the LCp -used in the bootp request as the key to identify the LCp during the BOOTP process.

The IP address to be used by the LCp.
The subnet mask to be used by the LCp.
The hardware type should be set to ethernet.

If the Bootp server is on a different network (requiring  a relay agent) then the relay agent must set the gateway address field of the bootp response.

The log server should be set (this may be defaulted to 0.0.0.0 if required.
If an authorization problem is detected a trap will be generated to this address.

The name of  the LCp configuration file to be read from the TFTP server by the LCp.

The time offset of the LCp from GMT. -used to calculate the local time for use in filed support log.



LCp Binary Configuration File Format

The LCp specific configuration data is contained in a file which is downloaded to the LCp via TFTP.  This is a binary file in the same format defined for bootp vendor extension data (RFC 1533).
It consists of a number of options (1 per parameter) each of the form
code:	length:	value
where code is a single octet identifier which defines the parameter
length is a single octet containing the length of the value field (not including code and length fields)
value is from one to 254 octets containing the specific value for the parameter

The options follow each other directly in the file which is a stream of octets (no record markers).

To avoid a bug in the Netmanage TFTP server the binary file is converted to hexadecimal data and the ascii representation of this (in the range 0x30 to 0x46, 0 through f) transferred to the LCp.  This doubles the size of the file unfortunately. The maximum size of the MD5 file is 16384 bytes.  Note that this is the last step in the file creation process, after the MD5 digest has been calculated.  

e.g.	binary		hex		asciihex transferred to LCp
	01001001	49		3439


Not all options need to be present in a given file.

The following options are supported:

end option
This is a special marker for end of data.
It has no length or value fields.

	code	
	255

pad option.
This has no length or value fields and is only used following the end of data option to pad the file to an integral number of 32 bit words.

	code	
	0

transmit frequency option
The transmit frequency to be used by the LCp.  This is the center frequency of the Unilink Channel in kHz stored as a 32 bin binary number where tx1 is the most significant byte, tx4 is least.

	code	length		tx frequency
	1	4		tx1 tx2 tx3 tx4

Software Revision Option
The value of this field specifies the revision id of the current software which is resident on the TFTP file server.  If this option is present the modem will check its current s/w revision and if the code on the server is a later revision the modem will perform a s/w upgrade.  The revision is passed as an integer number which is calculated by multiplying the s/w revision (given to two decimal places) by 100.
Thus s/w revision 3.21 would be encoded as 321.

	code	length		value
	33	4		s/w revision * 100

Software Upgrade Filename Option
The value of this field specifies the filename of the current software which is resident on the TFTP file server.  Only a simple filename not a full path name is used -the file must be resident in the default TFTP directory on the server.  If the s/w revision option is not present this option is not used. The maximum length of the filename is dependent on the TFTP server operating system but may not be longer than 64 bytes.

	code	length		value
	34	variable		ônewfile.exeö

Explicit Steps During File Creation

The sequence of operations required to create the configuration file are as shown below.

1.
Create the type length value entries for all the parameters required by the LCp





1A.
Create the type length encoded VarBind entries for all the filter parameters in the configuration file.  These are optional parameters which can be provisioned.






1B.
Create the encoded VarBind entries for each of the parameters entered in the configuration file.   This requires building the ASN.1 Object Identifier and then building the ASN.1 data field based on the type of data being encoded.  After the object and data fields are built, an ASN.1 sequence must be built.  This sequence contains a header with an id and length specified.  The encoded VarBinds become the standard data field in the format code, length, data file entries.



                   


2. 
Calculate the MD5 digest by pre-pending the 64 byte authentication key data to the parameter data and calculating the digest over the combined key and parameter values.







3.
Remove the authentication data and add the 16 byte MD5 digest following the last parameter using code and length values defined for this field.







4.
Add the end of data marker.






5.
Convert the file into hexadecimal data.
